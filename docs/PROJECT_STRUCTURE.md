## Folder responsibility rules

| Folder | What goes in | What does NOT go in |
|---|---|---|
| `app/api/` | Thin HTTP handlers — validate input, call service, return JSON | Business logic |
| `lib/services/` | All business logic; wraps Prisma in `$transaction` | React imports, JSX |
| `lib/schemas/` | Zod schemas only | Anything else |
| `components/` | Presentational + interactive React components | Direct Prisma calls (use hooks/services instead) |
| `hooks/` | React Query wrappers around API calls | Business logic |
| `lib/utils/` | Pure helpers (formatting, dates, math) | Anything stateful |

---

## Why this structure?

1. **Service layer is the brain.** "Recording a sale" is one function in `lib/services/sales.ts` that touches 4 tables inside a transaction. The route handler is 5 lines: parse → validate → call service → return JSON. Any future caller (server action, CLI script, scheduled job) can reuse the service.
2. **Schemas shared between client & server.** A Zod schema in `lib/schemas/sale.ts` is imported by both the React form (for client validation) and the API route (for server validation). One source of truth.
3. **Hooks isolate data fetching.** Components don't know about URLs — they call `useSales()` and get `{ data, isLoading, error, mutate }`. If we switch to server actions later, only the hook changes.
4. **Mobile-first layout enforced.** `Screen.tsx` wraps every page in a max-width mobile container, so we never accidentally build desktop-first.
